\section{Static Storage Class}

\subsection{Step 1: Program with static (\texttt{static1.c})}

\begin{lstlisting}[style=cstyle]
#include <stdio.h>
#include <stdlib.h>

void main()
{
    auto int x = 3;
    while (x > 0)
    {
        static int y = 5;
        y++;
        printf("The value of y is %d\n", y);
        printf("The address of y is %p\n\n", &y);
        x--;
    }
}
\end{lstlisting}

\textbf{Compile and run:}
\begin{lstlisting}[style=bashstyle]
gcc -o static1 static1.c
./static1
\end{lstlisting}

\textbf{Output (run 3 times):}
\begin{lstlisting}[style=outstyle]
===== RUN 1 =====
The value of y is 6
The address of y is 0x5710b515b010

The value of y is 7
The address of y is 0x5710b515b010

The value of y is 8
The address of y is 0x5710b515b010

===== RUN 2 =====
The value of y is 6
The address of y is 0x5fdf88e3f010

The value of y is 7
The address of y is 0x5fdf88e3f010

The value of y is 8
The address of y is 0x5fdf88e3f010

===== RUN 3 =====
The value of y is 6
The address of y is 0x60520d2df010

The value of y is 7
The address of y is 0x60520d2df010

The value of y is 8
The address of y is 0x60520d2df010
\end{lstlisting}

\subsubsection*{Explanation for Step 1}
\begin{itemize}
    \item \textbf{Within a single run:} The variable $y$ is declared as \texttt{static int y = 5;}. Even though it is declared inside the \texttt{while} loop body, the initialization occurs only once at program startup. The variable is allocated in the \textbf{Data Segment} (static memory) rather than on the stack. Therefore, when the block exits and re-enters across loop iterations, $y$ is not re-initialized, preserving its value and accumulating from $5 \to 6 \to 7 \to 8$. Its address remain completely identical within the same run.
    \item \textbf{Between different runs:} Each time the program is executed, the virtual memory address of $y$ changes (e.g., \texttt{0x5710...}, \texttt{0x5fdf...}, \texttt{0x6052...}). This is because GCC compiles executables as \textbf{PIE (Position Independent Executable)} by default, allowing the operating system to apply \textbf{ASLR (Address Space Layout Randomization)} to randomize the program's base load address for security.
\end{itemize}

\subsection{Step 2: Program without static (\texttt{static2.c})}

\subsection{Step 3: Explanation and Discussion of Difference}

\subsubsection*{Why do the results show up that way in Step 2?}
Without the \texttt{static} keyword, $y$ becomes an \textbf{automatic local variable} (equivalent to \texttt{auto int y = 5;}). 
\begin{itemize}
    \item \textbf{Value is always 6:} An automatic variable has \textbf{block scope} and \textbf{automatic storage duration}. In each iteration of the \texttt{while} loop, $y$ is allocated anew on the \textbf{Stack Frame}, initialized to $5$, incremented to $6$, and deallocated when the block ends. Hence, the value does not accumulate and is printed as $6$ in every iteration.
    \item \textbf{Stack Address:} The address of $y$ is in the range \texttt{0x7ffc...} / \texttt{0x7ffd...}, which corresponds to the user stack region near the top of the virtual address space, rather than the data segment.
\end{itemize}

\section{Extern Storage Class}

\subsection{Step 1: Program with extern in main (\texttt{extern1.c})}

\begin{lstlisting}[style=cstyle]
#include <stdio.h>
#include <stdlib.h>

int x = 20;

void display()
{
    extern int x;
    printf(" Display value of x: %d\n", x);
    printf(" Adress of x (in display function): %p\n\n", &x);
}

void main()
{
    extern int x;
    printf(" Print value of x: %d\n", x);
    printf(" Adress of x (in main function): %p\n\n", &x);
    display();
}
\end{lstlisting}

\textbf{Compile and run:}
\begin{lstlisting}[style=bashstyle]
gcc -o extern1 extern1.c
./extern1
\end{lstlisting}

\textbf{Output (run 3 times):}
\begin{lstlisting}[style=outstyle]
===== RUN 1 =====
 Print value of x: 20
 Adress of x (in main function): 0x582057aa2010

 Display value of x: 20
 Adress of x (in display function): 0x582057aa2010

===== RUN 2 =====
 Print value of x: 20
 Adress of x (in main function): 0x6451fd93b010

 Display value of x: 20
 Adress of x (in display function): 0x6451fd93b010

===== RUN 3 =====
 Print value of x: 20
 Adress of x (in main function): 0x557625310010

 Display value of x: 20
 Adress of x (in display function): 0x557625310010
\end{lstlisting}

\subsubsection*{Explanation for Step 1}
Both \texttt{main()} and \texttt{display()} print the value $x = 20$ and reference the exact same memory address within each run. This is because $x$ is a \textbf{global variable} allocated in the static data segment. The keyword \texttt{extern} specifies that the variable is defined with external linkage (or in outer/file scope). Since both functions refer to the same symbol $x$, they point to the identical address in the Data Segment. Furthermore, across different runs, the address changes due to PIE and ASLR.

\subsection{Step 2: Program without extern in main (\texttt{extern2.c})}

In this step, we delete the declaration \texttt{extern int x;} on line 15 inside \texttt{main()}:

\begin{lstlisting}[style=cstyle]

 Display value of x: 20
 Adress of x (in display function): 0x63d1d3f0c010

\subsubsection*{Explanation: Why do the results show up that way?}
In C, any variable defined outside of all functions has \textbf{file scope} and \textbf{static storage duration} by default, making it accessible from any function defined below it in the same translation unit without needing an explicit \texttt{extern} declaration.
\begin{itemize}
    \item When \texttt{extern int x;} was present in \texttt{main()}, it was simply an explicit declaration telling the compiler to look for $x$ in the global/external scope.
    \item When \texttt{extern int x;} is deleted, since there is no local variable named $x$ inside \texttt{main()}, the compiler automatically resolves $x$ to the global definition \texttt{int x = 20;}.
    \item Therefore, both \texttt{main()} and \texttt{display()} still refer to the exact same global variable $x$.
\end{itemize}

\subsubsection*{Discussion: Differences Between Both Outputs}
The outputs of \texttt{extern1} and \texttt{extern2} are \textbf{functionally identical} in terms of value ($20$) and address sharing between \texttt{main()} and \texttt{display()}:
\begin{itemize}
    \item In \texttt{extern1.c}: The \texttt{extern} inside \texttt{main()} is redundant because $x$ is already defined globally earlier in the same file.
    \item In \texttt{extern2.c}: Removing \texttt{extern} does not change the behavior, as global variables are inherently visible to all functions in the file.
    \item \textbf{When is \texttt{extern} actually necessary?} \texttt{extern} is strictly required when a global variable is defined in \textit{another separate source file} (multi-file compilation), or when a function needs to reference a global variable that is defined \textit{later} in the same file below that function.
\end{itemize}

    \item Both \texttt{extern1\_nopie} and \texttt{extern2\_nopie} yield the exact same fixed address \texttt{0x404018} across all runs.
\end{itemize}

\begin{table}[ht!]
\centering
\small
\begin{tabular}{@{}p{3.5cm}p{3.2cm}p{8.5cm}@{}}
\toprule
\textbf{Part} & \textbf{Value} & \textbf{Meaning} \\
\midrule
Address of Pointer \verb|&a| & \verb|0x7ffd90c86520| & Address of pointer variable $a$ itself, located on the \textbf{Stack} (prefix \texttt{0x7ffd...}); separated by 8 bytes from \verb|&b| (64-bit pointer). \\

\verb|&a[9]| & \verb|0x5fad2e71e2d4| & Offset from \verb|&a[0]| = $9 \times 4$ = 36 bytes (\texttt{sizeof(int)} = 4 bytes). \\

\bottomrule
\end{tabular}
\caption{Interpretation of each memory section in Step 1.}
\end{table}

\textbf{Key Takeaways for Step 3:}
\begin{itemize}
    \item Local pointer variables (\texttt{\&a}, \texttt{\&b}) and local arrays (\texttt{c}) reside on the \textbf{Runtime Stack}.
    \item Dynamic buffers returned by \texttt{malloc()} and \texttt{realloc()} reside on the \textbf{Heap}.
    \item The effective address of an unallocated pointer is \texttt{(nil)} (\texttt{NULL}).
\end{itemize}

\subsection{Step 6: Analysis and Discussion (In-Place vs Relocated Realloc)}

\subsubsection*{Why do the results show up that way?}
\begin{itemize}
    \item \textbf{Allocation of block $b$:} After \texttt{malloc}, pointer $b$ receives the address \texttt{0x604b...2e0}. Notice that block $a$ ends around \texttt{0x604b...2d8} ($10 \times 4 = 40$ bytes plus heap chunk header overhead), which means block $b$ is placed immediately adjacent to block $a$ on the heap.
    \item \textbf{Array $b$ offsets:} \verb|&b[0]| $= b$, and \verb|&b[9]| is located at offset $9 \times 4 = 36$ bytes (\texttt{sizeof(float)} = 4 bytes).
\end{itemize}

\subsubsection*{Comparison: Is the result different from the previous run? Especially for the address of array $a$?}
\textbf{Yes, fundamentally different!}
\begin{itemize}
    \item \textbf{In \texttt{mem1.c} (Without $b$):} 
    The address of $a$ after \texttt{realloc} remained \textbf{identical} (\texttt{0x5fad2e71e2b0}). Because no other heap block was allocated immediately following $a$, the glibc heap allocator expanded block $a$ \textbf{in-place} from 40 bytes to 4000 bytes without changing its starting virtual address.
    \item \textbf{In \texttt{mem2.c} (With $b$ allocated):} 
    The address of $a$ after \texttt{realloc} \textbf{changed} from \texttt{0x604b7e40b2b0} to \texttt{0x604b7e40b310}. 
    \item \textbf{Why?} Block $b$ occupied the memory immediately following block $a$, blocking contiguous in-place expansion. To satisfy the request of 4000 bytes (1000 ints), \texttt{realloc} was forced to:
    \begin{enumerate}
        \item Find a new, sufficiently large contiguous chunk of memory on the heap (starting at \texttt{0x604b7e40b310}).
        \item Copy the existing data from the old block $a$ to the newly allocated block.
        \item Free the old block $a$ back to the heap allocator.
    \end{enumerate}
\end{itemize}

\textbf{Conclusion for Step 6:} The presence of intervening dynamic allocations on the heap dictates whether \texttt{realloc()} can expand in-place or must relocate the buffer to a new address.
